    How the system works
    
    
    The text below follows the rules of ASD-STE100. Each sentence holds one fact. Each sentence uses one action.
    

    
    
      
    
        
    Admission control
    
        
      
          
    • A sandbox request passes through four gates. The gates are the control plane, the relay, the worker queue, and the pool budget.
      • 
          
    • The control plane checks the enrollment list first. Then the control plane counts the live sandboxes. The count runs in one Lua script. The script is atomic. Two requests cannot take the same free slot.
      • 
          
    • The quotas control disk, not memory. A user holds at most 3 live sandboxes. The service holds at most 40 live sandboxes.
      • 
          
    • The control plane does no worker I/O at create time. The worker builds the workspace at the first Exec.
      • 
          
    • The relay caps the in-flight Execs per sandbox. The default cap is 2. One Exec runs. One Exec waits at the workspace gate.
      • 
          
    • The worker holds a queue of 64 Execs. The queue answers busy: queue full when it is full.
      • 
          
    • The pool checks the memory budget. The check adds the full price of one VM to the committed bytes. The price is guest RAM plus VM overhead.
      • 
          
    • A paused standby costs less than a running VM. The pool charges the measured dirty pages times the headroom factor.
      • 
          
    • A promotion over the budget evicts standbys from colder runs. The eviction picks the run with the oldest last use first.
      • 
          
    • Every refusal is retryable. The caller sees HTTP 429, HTTP 503, or RESOURCE_EXHAUSTED. Each refusal carries a distinct reason code.
      • 
        
    
      
    
      
    
        
    Pool management
    
        
      
          
    • The pool groups VMs by workspace. Each workspace is one run.
      • 
          
    • The pool keeps standby VMs for each run. A standby VM is paused. The target count per run is 2.
      • 
          
    • An Exec acquires one standby. The acquire pops the newest standby first.
      • 
          
    • The VM runs one command. The pool destroys the VM after the command. The pool never reuses a VM.
      • 
          
    • The destroy runs as a deferred step. The background workers finish the reap. The workspace gate opens at the barrier.
      • 
          
    • The pool refills a popped slot after a delay. The delay is 200 ms. The delay keeps a finished run from getting new VMs. A failed refill backs off. The backoff starts at 250 ms, doubles, and stops at 30 s.
      • 
          
    • The sweep runs on every Exec. The sweep also runs on a timer. The timer fires every 22.5 s.
      • 
          
    • A run with no Exec for 90 s drops its standbys. The run keeps the workspace. The run enters the state parked. A parked run holds disk, not memory.
      • 
          
    • The sweep destroys at most 8 VMs per scan. This rate limits the reclaim work.
      • 
          
    • A run with no Exec for a longer time loses the workspace. The default time is 30 minutes. A sandbox-service deployment typically sets it longer than the sandbox lifetime (for example 216 hours). A live sandbox keeps its workspace for its whole lifetime.
      • 
          
    • The host janitor runs every 15 minutes. The janitor asks the control plane for the live and terminated sandboxes. The janitor frees the disk of a terminated sandbox after a grace period.
      •
